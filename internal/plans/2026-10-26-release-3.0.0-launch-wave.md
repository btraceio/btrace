# BTrace 3.0.0 launch wave: announcement copy, demo scripts, feature tutorials

Status: proposed 2026-10-26, awaiting approval.

## Audience and angle (decided)

- Primary: existing BTrace 2.x users and people who already use Java tracing tools. Lead with what
  changes their day-to-day on Monday morning, not with "what is dynamic tracing".
- Second headline, with equal weight: the AI tooling. The `btrace-observability` plugin for Claude
  Code, Codex and Pi (skills plus a stdio MCP server, external `btraceio/agent-plugins` repo) and
  the bundled AI-workload extensions: `btrace-llm-trace`, `btrace-rag-quality`, `btrace-gpu-bridge`,
  `btrace-contracts`.

### Day-to-day features to lead with (in this order)

1. Oneliners: `btrace -n '...' <pid>`, no file, no compile.
2. Flat DSL and auto-imports: scripts lose the `BTraceUtils.` prefix and the import block.
3. `btrace doctor` plus authenticated prepared mode (`port=0`): the "why will it not attach" hour.
4. Extensions replace `Aggregations` and `libs=` profiles; `btrace-metrics` gives HdrHistogram
   percentiles; `-le` and `btracex` explain a blocked extension instead of failing silently.
5. Upgrade cost: compiled probes need nothing; source scripts get a one-line import fix
   (`scripts/migrate-btrace-script.sh`).

Second paragraph material: single `btrace.jar`, Apache 2.0, V2 wire protocol with V1 fallback,
ClassFile API backend for class files newer than the ASM ceiling, Docker images, fat agents.

### AI "big bang" story

- "Ask your coding agent why `POST /orders` is slow. It writes the probe, attaches, reads the
  output, and retracts it." The plugin is skills first, MCP second; the copy says so.
- One probe per AI workload type: LLM calls (tokens, cost, latency budget), RAG retrievals (empty
  hits, top scores, retrieval versus generation split), on-device inference (ONNX, DJL,
  TensorFlow Java). No SDK in the app, no log shipper.

### Third headline: the single biggest wow (decided 2026-10-26)

Overall, the coding-agent plugin is the biggest wow in 3.0.0 and the AI post leads with it. As a
third demo and tutorial area distinct from the two above, the pick is **"attach to production
without fear"**: a JVM started with `-javaagent:btrace.jar=port=0` exposes a loopback, token
protected endpoint; `btrace doctor <pid>` says whether it is ready before anything is loaded; a
3.0 client finds the token through the Attach API with no flags; and when the client exits, the
`invokedynamic` call sites the probe left behind become no-ops, so retracting a probe leaves no
lingering overhead. For people who already use tracing tools this is the credibility story, and
it is demoable and QE-able on the JDKs installed here. Runner-up was the ClassFile API backend
(tracing Java 28 class files ASM cannot parse); it is a real wow for JVM people but needs a JDK 28
build to demo, which this machine does not have, so it stays a release-notes bullet.

The press release names all three headlines in its first paragraph: no-file oneliners, the coding
agent, and production-safe attach.

### B2. QE coverage of the demos (`btrace-qe`)

The harness today has two modes: `target` (launch an app with the agent, check it stays alive)
and `client` (run the CLI, check exit code). A demo needs a third shape: launch the app without
the agent, attach the client with a probe or oneliner, wait for expected output lines, detach,
stop the app. Work:

1. New `given.mode: attach` with steps `launch`, `awaitReady`, `attach`, `awaitOutput`, `detach`,
   `shutdown`, `awaitExit`; `given.target` may name a demo app (compiled from `demos/` by a new
   `demoTargets` source set) and `given.clientArgs` carries the probe or oneliner. Expectation
   `outputMustMatch:` (regex list, in order). TDD in `btrace-qe` self tests, then the executor.
2. New surface `demos` with one YAML case per `run.sh` scenario (scenarios 01 to 05 and 07; 06
   has no automatable client). Scenario 07 additionally uses the existing `target` mode shape,
   since its app starts with the agent. The case replays the same commands `run.sh` runs; `run.sh` and the YAML
   read the commands from the same `commands.txt` so they cannot drift.
3. `./gradlew :btrace-qe:qe -Pqe.surface=demos` is the gate; the tutorials index documents it.
4. btrace-qe is not wired into any GitHub workflow today. Adding it is a workflow-file change and
   is proposed separately, not done here, unless you say so.

Scenario 06 (coding agent) cannot be made deterministic; its `run.sh` is covered as far as
starting the app, and the prompt script is verified by hand against the plugin README.

## Findings while building the demos (2026-10-26)

Running the scenarios end to end against the SNAPSHOT distribution exposed product bugs:

| # | Finding | Status |
|---|---|---|
| 1 | Oneliner method and class wildcards (`OrderService::*`, `get*`, `javax.swing.*`) never matched: the generator emitted them verbatim and the agent matches exact names or `/regex/` only. Breaks tutorial 01 step 4 and most of `docs/OnelinerGuide.md`. | fixed in `OnelinerCodeGenerator.toProbePattern`, 7 unit + 2 integration tests |
| 2 | Probes compiled with BTrace 2.2.6 (packed and `-nopack`) fail the verifier before the `org/openjdk/btrace` rewrite runs. Contradicts "compiled probes need no change". | fixed: `ProbePackageMigrator` runs before verification in both loaders and also remaps the 2.x runtime glue (`BTraceRuntimeImplBase` → `BTraceRuntimeBridge`), `ldc` constants and frames; packed probes get their handlers restored. Unit tests on real 2.2.6 output plus `testLegacyPackedProbe` |
| 3 | Every `@Injected` field read site bootstraps its own service instance, so an `@OnTimer` dashboard sees an empty service while `@OnMethod` handlers record. Breaks tutorial 07 step 6. | fixed: `ExtensionIndy` caches one instance per (probe class, service); `HandlerRepositoryImpl.unregisterProbe` invalidates it. Unit test plus `testInjectedServiceInstanceSharedAcrossHandlers` |
| 4 | `BTraceClassReader`'s reflective hook into ASM `ClassReader.readElementValue` broke with ASM 9.11.1 (new `int depth` parameter); logged at DEBUG only. | fixed, and the hook had been calling the wrong ASM method (`readElementValue` instead of `readElementValues`) all along, so annotation matching was off before the upgrade too. `BTraceClassReaderTest` pins the bundled ASM signature |
| 5 | False alarm: throughput "not recovering" after detach was a demo-side artifact (client killed instead of exited). With a clean exit the agent retransforms the class back and throughput returns to baseline within seconds (verified with `-XX:+PrintCompilation`). | demo helper fixed |

| 6 | `java -javaagent:btrace.jar=port=0 App.java` (single-file source launch) dies on JDK 25 and 26: the agent jar on the boot class path carries `META-INF/services/javax.annotation.processing.Processor` (the `@ExternalType` processor for extension builds), javac's processor discovery loads it from the boot loader and fails (`NoClassDefFoundError: javax/annotation/processing/AbstractProcessor`; on 26 the launcher reports "Could not find or load main class App.java"). Works on 17 and 21. Found by the harness session running demo 07 on JDK 26. Proposed fix: drop the service entry from the shipped jar and have the `io.btrace.extension` Gradle plugin pass `-processor io.btrace.extension.processor.ExternalTypeProcessor`; integration test launching a source file with the agent. | fixed: service entry excluded from `btrace.jar` (packaging test, release verifier check), plugin passes `-processor` (TestKit test), `AgentSourceLaunchIntegrationTest` red on JDK 26 then green on 26 and 17; demo 07 runs from source on JDK 26 |
| 7 | `generateServiceShims` in the extension Gradle plugin declares outputs but no inputs, so adding a method to a service interface leaves stale shims (`compileServiceShims` then fails until `clean`). | fixed: the task now declares the authored classes and the export settings as inputs; TestKit test changes the interface between two builds |
| 8 | The agent-plugins MCP server dropped all probe output after startup, so an assistant could deploy and remove probes but never read what they found. | fixed in agent-plugins (uncommitted): bounded per-probe buffer (64 KB, oldest lines dropped and counted), new `read_probe_output` tool with an optional `wait_seconds` (max 30, collects a report until 150 ms of quiet), `exit_probe`/`detach_probe` return unread output; unit, e2e and eval case added. Tutorial 05 depends on this shipping in the plugin |
| 9 | `@Duration` at `Kind.RETURN` is 0 at every return instruction after the first in bytecode order (ASM backend), so `@return if duration>...` misses the normal path of any method with an early return. The ClassFile API backend is not affected. | fixed: `Instrumentor` resets the duration flag per return site; `testReturnDurationWithEarlyReturn` red then green on JDK 17 and 26; golden data for 7 multi-return cases regenerated |
| 10 | At `Kind.ERROR` an unannotated `Throwable` parameter is matched against the target's arguments, fails validation, and the handler is silently not applied. The Tutorial, Quick Reference, Troubleshooting, tutorial 06 and its `OrderCounterProbe`, and the plugin skill all show the bare `Throwable` form; recorded assistants write it too. `@TargetInstance Throwable` works. | fixed (decided: bind it): `BTraceMethodNode` binds the last unannotated `java.lang.Throwable` at `Kind.ERROR` when no `@TargetInstance` is present; golden fixture `ErrorBareThrowable` and `testErrorHandlerWithBareThrowable` red then green on JDK 17 and 26; Quick Reference documents the rule. `CATCH`/`THROW` still need `@TargetInstance` (Quick Reference corrected) |
| 11 | `list_jvms` keeps reporting `BTrace: attached` after `exit_probe`, because the agent stays loaded; assistants then cannot state that nothing is attached. | open: wording in the MCP server (agent loaded vs probes running) |
