## 2. Java-version claims are a three-way contradiction (blocker)
- `docs/GettingStarted.md:17` — "Java 8 or higher (BTrace supports Java 8-20)" (repeated at :833)
- `docs/FAQ.md:33,443` — "Java 8 through Java 20"
- `docs/Troubleshooting.md:579` — "BTrace supports Java 8+" (while :561 documents JDK 25 behavior)
- `docs/README.md:154` — "Java Compatibility: Java 8-25"
- `docs/MCPServer.md:13` — MCP needs JDK 11+ (fine, but should be restated relative to the new floor)
- `docs/releasing.md:43` — integration tests on 8/11/17/21

3.0 target statement (single canonical formulation to use everywhere):
> BTrace 3.0 runs on Java 8–25+. Running on Java older than 17 is **deprecated**: it works fully in 3.x but prints a deprecation warning, and support will be **removed in the next major release (4.0)**.

22. **`list_probes` MCP tool semantics were documented backwards everywhere they appeared** (`ListProbesHandler.schema()`'s own tool description, `docs/MCPServer.md`'s tool table + Typical Workflow + a troubleshooting step, `docs/BTraceTutorial.md` Lesson 13's tool table + example transcript): all described it as listing "active"/"currently deployed" probes. The actual implementation — `io.btrace.agent.Client.listProbes()`, filtering on `RemoteClient.isDisconnected()` — only returns probes a client has *detached* from and could reconnect to via the plain CLI's `-r` flag; a probe still connected to its client never appears. Compounding this: the MCP server exposes no `reconnect` tool among its seven, so `detach_probe` is a one-way action from an AI assistant's perspective — nothing in the tool set can `send_event` or `exit_probe` a probe once detached. Found and fixed in all four places while independently verifying tutorial T7 (`docs/tutorials/05-mcp-server.md`) against source; also fixed `docs/BTraceTutorial.md` Lesson 13's launch command (was `java -jar btrace-mcp-server.jar` — the jar is not self-contained) and a fabricated `-Dbtrace.port`/`BTRACE_PORT` global-override claim with no basis in source (`port` is a per-call argument only, no env var support). **Recommend for the release plan:** either add a `reconnect_probe` tool before 3.0 ships the MCP server as a headline feature, or prominently document `detach_probe`'s one-way nature so users don't lose track of running probes.
23. **`BTraceExtensionPlugin.groovy`'s annotation-based auto-detection is pervasively dead code for 3.0-style extensions.** Found while independently verifying tutorial T5 (`docs/tutorials/06-write-your-own-extension.md`). At least 11 call sites across `BTraceExtensionPlugin.groovy` and `SingleSourceApiPartition.groovy` hardcode the bytecode descriptor `Lorg/openjdk/btrace/core/extensions/ServiceDescriptor;` / `Lorg/openjdk/btrace/core/extensions/ExtensionDescriptor;` (the pre-3.0 package) instead of `Lio/btrace/core/extensions/...;` — so any auto-detection of service interfaces or extension metadata from annotations silently finds nothing against a real 3.0-package extension. The workaround (declare `services = [...]` explicitly in `btraceExtension {}`) is harmless and is what `btrace-metrics` and the new tutorial both already do, but the auto-detection feature itself is effectively non-functional in this checkout and should either be fixed (rename the descriptors) or have its "auto-detect" claim removed from `BTraceExtensionDevelopmentGuide.md` if one exists there. Fixed the one place this leaked into user-facing docs: `docs/BTraceTutorial.md`'s "Writing Your Own Extension (Quick Start)" section, which also had two smaller bugs from the same drift — `import io.btrace.ext.spi.Extension` (real package is `io.btrace.core.extensions.Extension`) and an invented `api`/`impl` subpackage split that doesn't match how `btrace-metrics` or the plugin's own single-source-tree model actually work.
24. **Fat-agent embedding silently bypasses the privileged-permission gate.** Found while independently verifying tutorial T8 (`docs/tutorials/08-fat-agent.md`). `EmbeddedExtensionRepository.java:243` hardcodes `.requiredPermissions(PermissionSet.empty())` when parsing any embedded extension (both the Gradle `io.btrace.fat-agent` plugin's output and the Maven `fat-agent` goal's output), so `ExtensionBridgeImpl.requiresPrivileged()` always returns `false` for embedded extensions regardless of what the extension actually declares — the same privileged-tier gate that Lesson 6 / Tutorial 4 demonstrate for filesystem-installed extensions never applies once an extension is baked into a fat agent. Concretely: embedding a `THREADS`-requiring extension like `btrace-metrics` into a fat agent ships it active for anyone who runs the resulting jar, with no policy file, no opt-in, and no way to deny it after the fact. This is a real security-relevant gap for a "package once, run anywhere" feature and should be decided on deliberately (either enforce the real permission set for embedded extensions, or document loudly that embedding *is* the grant) before 3.0 ships fat agents as a supported path.
25. **Fat-agent "bundled probes" (zero-config startup probes) are a silent no-op.** Also found verifying T8. The Gradle plugin's `stageProbes` task stages compiled probe classes to `META-INF/btrace-probes/` inside the jar, matching what `docs/architecture/fat-agent-plugin.md` and (per the T5/T8 agents) `docs/BTraceExtensionDevelopmentGuide.md` describe — but `Main.loadProbesFromNames()` at runtime only ever looks for bundled probes under `META-INF/btrace-extensions/<extension-id>/probes/`, sourced from an embedded extension's own `extension.properties`. Nothing reads `META-INF/btrace-probes/` at runtime, so passing `probes=YourProbe` on a fat agent built with `bundledProbes {}` logs a real, verified "Loading bundled probes: YourProbe" line and then silently finds nothing — no error. Either wire the loader to also check the Gradle-staged path, or fix the two docs that currently promise this works.
26. **Maven's `fat-agent` goal has a classifier mismatch and a `.classdata` path mismatch that likely break extension embedding end to end.** Also found verifying T8. `FatAgentMojo.processExtension()` resolves an extension's implementation via classifier `"impl"`, but `BTraceExtensionPlugin.groovy`'s `maven-publish` block never attaches a plain `impl`-classified artifact (only `api`, `api-sources`, `api-javadoc`, `extension` — confirmed by grepping the whole tree for `classifier = 'impl'`: no matches). Separately, even when an impl jar is found, `FatAgentMojo.stageImplClasses()` writes `.classdata` under a nested `META-INF/btrace-extensions/<id>/impl/...` path, while `ClassDataLoader.findClass()` looks them up flat by class name from the jar root — the layout the Gradle plugin actually produces. Both are plausible-looking, untested code paths that would fail silently (impl lookup failure is logged only at `debug`) rather than loudly. Needs a real end-to-end Maven build against published 3.0.0 artifacts to confirm and fix before this goal is documented as supported.
27. **`docker/README.md`'s "Pattern 4: Distroless Production" snippet used the stale pre-3.0 two-JAR invocation** (`-javaagent:...btrace-agent.jar` + a separate `-Xbootclasspath/a:...btrace-boot.jar`, and `gcr.io/distroless/java11` instead of the Dockerfile's actual pinned `gcr.io/distroless/java11-debian11`) while every other current doc in the tree (`GettingStarted.md`, `Troubleshooting.md`, `FAQ.md`, `BTraceTutorial.md`, `MaskedJarArchitecture.md`) already uses the correct single masked `btrace.jar` form. Found and fixed while independently verifying tutorial T9 (`docs/tutorials/09-kubernetes-sidecar.md`). Also confirmed the Docker image build tasks (`buildDockerImage`, `buildDockerImageAlpine`, `buildDockerImageDistroless` in `btrace-dist/build.gradle`) depend on `btraceJar` but never on `fatAgentJar` — so a pulled official image never contains the fat-agent jar unless a release pipeline explicitly builds and adds it; worth a one-line callout in `docker/README.md` for anyone combining Lesson 14's two packaging paths.

## 4. Missing documents (to create)
1. **`docs/Migration-2.x-to-3.0.md`** — the single most important missing doc for this release. It can (and should) be short, because most migration is automatic; its job is to say so authoritatively:
   - Compiled/persisted probes: **no action** — `ProbePackageMigrator` remaps `org/openjdk/btrace/` → `io/btrace/` transparently at load time.
   - Script sources: mechanical import rewrite (`org.openjdk.btrace` → `io.btrace`); with the new auto-imports most scripts can simply *drop* the imports. Ship/point to an automated rewrite (sed one-liner or helper script — see release plan Phase 3 item 3a).
   - The rest is a checklist: Maven coordinates `io.btrace:*`, masked-JAR packaging change, `btrace-instr` artifact removal, libs→extensions migration pointer, wire-protocol compatibility statement, Apache-2.0 note, and the Java < 17 deprecation policy with the 4.0 removal notice.
