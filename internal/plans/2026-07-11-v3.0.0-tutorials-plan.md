# BTrace 3.0 — User-Engaging Tutorials & Content Plan

Date: 2026-07-11
Inputs: `2026-07-11-v3.0.0-feature-map.md` (feature inventory), `2026-07-11-v3.0.0-docs-gap-analysis.md` (§5 tutorial findings).
Scope: ALL new 3.0 features, across four channels — hands-on guided tutorials, a blog-post series, extensions to `docs/BTraceTutorial.md`, and screencast/video scripts. Includes one pilot tutorial (shipped alongside this plan) that sets the template.

**Interface flexibility note**: a rich terminal UI ("BTrace Console", built on TambouI) is currently a *design prototype only* — no code exists yet, and its scope for 3.0.0 is undecided. This plan and its tutorials are written CLI-first (the shipping interface) but structured so that if/when the TUI lands, tutorial content extends rather than gets rewritten — see §3a.

## 1. Goals and audiences

Goal: a user who lands on any channel can go from "never used BTrace" to a successful trace in minutes, and from there to the 3.0 feature that solves their problem — without hitting a stale command or an unverified claim.

Personas (each tutorial declares exactly one primary persona):

| Persona | Cares about | Entry channel |
|---|---|---|
| **Firefighter** (ops/SRE) | diagnose a live JVM *now*, zero prep | oneliners, Docker sidecar |
| **Instrumenter** (Java dev) | expressive scripts, repeatable probes | flat DSL, extensions |
| **Platform engineer** | packaging, CI, K8s, Spark/Hadoop | fat agent, Docker, plugins |
| **AI-tooling user** | LLM/RAG/GPU observability, MCP | AI extensions, MCP server |
| **2.x upgrader** | "what breaks, what do I do" | migration tutorial |

## 2. Engagement principles (apply to every artifact)

1. **Time-boxed promise in the title** ("…in 2 minutes") and honor it — the first success must arrive before the first concept.
2. **One shared demo app** (`docs/tutorials/demo/DemoApp.java`, single-file, zero dependencies, `java DemoApp.java` to run) reused across tutorials so setup is paid once. It simulates an order service with a latency defect and an intermittent failure — every tutorial "finds" something real.
3. **Checkpoints**: after every command, a "You should see:" block with realistic output. A reader who doesn't see it gets an inline "If not →" pointer.
4. **"What just happened"** boxes after each success — the concept is explained *after* the payoff, never before.
5. **Verified commands only**: every command/flag/output in a tutorial must be traced to code (same discipline as the docs sync). Each tutorial's PR description lists the code anchors it was verified against.
6. **Copy-paste safety**: commands are complete (no `<placeholders>` except `<PID>`), and each tutorial ends with a cleanup step.
7. **Show, then link**: tutorials never duplicate reference docs; they end with "Go deeper" links (OnelinerGuide, QuickReference, architecture docs).
8. **Terminal recordings**: each hands-on tutorial gets an asciinema/VHS-generated GIF of the happy path (also reused by the blog + video channels). Store `.tape`/cast sources under `internal/tutorial-assets/`, rendered GIFs under `docs/tutorials/images/`.
9. **Goal-first, interface-second narration**: phrase steps as "deploy a probe" / "watch the histogram" / "detach cleanly", with the CLI command as the *mechanism*, not the subject. Avoid framing that only makes sense for a text terminal ("type this command and read the scrolling text") when a goal-first phrasing ("deploy the probe — here's how from the command line") works just as well and doesn't need rewriting if an alternate interface (BTrace Console TUI) is added later. See §3a.

## 3. Channel strategy — single source of truth

`docs/tutorials/` (hands-on series) is **canonical**. The other three channels derive from it:

- **BTraceTutorial.md** stays the *conceptual* reference (its 13 lessons). Each lesson gains a one-line "Hands-on lab: →" link to the matching tutorial; the two missing lesson areas (fat agent, backends/JDK-future) get short new lessons that mostly link out. No content duplication.
- **Blog posts** are narrative adaptations (problem story → the 3.0 feature → the same demo/GIF → link to the hands-on tutorial). Drafts live in `internal/blog-drafts/` until published.
- **Video scripts** are shot-by-shot storyboards of a tutorial's happy path (see template §7). Scripts live in `internal/tutorial-assets/scripts/`.

## 3a. Interface tracks: CLI (shipping) vs BTrace Console TUI (exploratory)

Status: a design prototype for a rich TUI ("BTrace Console", TambouI-based, MIT-licensed, Java 8+
with 17+ recommended) exists as mockups/spec only — no implementation, no commitment to 3.0.0
scope. Treat it as **possible, not planned** until a decision is made. This section exists so that
tutorial work done now doesn't have to be redone if it ships.

**Principle**: `docs/tutorials/` stays CLI-canonical. The CLI is not going away even if the TUI
ships — the TUI's own design prototype explicitly reproduces every CLI action (the 7-option
Ctrl+C menu, `-le`, `btracex`) rather than replacing them. So CLI tutorials remain valid regardless
of the TUI's fate; nothing here is at risk of becoming wrong.

**What "flexible" means concretely**:
1. Tutorials describe the *goal* of each step before the *mechanism* (principle #9) so a "Prefer a
   visual view?" aside can be inserted later without restructuring prose.
2. Tutorial moments that the TUI design prototype specifically targets are flagged below as **dual-track
   candidates** — these are the first tutorials to get a TUI-equivalent variant if/when it ships,
   because the interaction they teach is exactly what the TUI replaces with a live view:
   - **T1** "Go deeper" / cleanup (Ctrl+C detach, the interactive menu) → TUI's Session screen.
   - **T2**/T1 `count` action's Ctrl+C → "send an event" flow → TUI's live counter/Gauge.
   - **T4** extensions, permissions, `-le`, `btracex` → TUI's Extensions screen (explicitly designed
     to absorb `btracex`'s existing lanterna TUI).
   - **T6** metrics/histogram output → TUI's Metrics tab (BarChart/Sparkline).
3. No tutorial should currently claim the TUI exists, ship a screenshot of it, or require it. Do
   not add "coming soon" callouts inside published tutorials — that's a maintenance liability if
   the feature slips or changes shape. Track TUI-readiness only in this internal plan.
4. If the TUI is greenlit for 3.0.0, add it as a proper coverage-matrix row (template: hands-on
   "T10 — BTrace Console: your first session", blog "B11 — a look inside BTrace Console", no
   video needed since it's inherently visual) and produce dual-track variants of T1/T4/T6 by
   *appending* a "Using BTrace Console instead" section to the existing files — never rewriting
   the CLI walkthrough.
5. Revisit this section once the TUI design prototype comes back from Design and a build/no-build
   call is made; update the status line above accordingly.

Per-tutorial production checklist: (a) run every command against a fresh RC build on at least JDK 17 + one pre-17 JDK where relevant; (b) capture asciinema; (c) code-anchor list in PR; (d) add to `docs/tutorials/README.md` index + `docs/README.md` learning paths; (e) for T1, T4, T6 — write steps goal-first (principle #9) since these are TUI dual-track candidates per §3a.

**Note on `count` semantics (verified)**: the counter print is emitted in an `@OnEvent` handler; in the client, `Ctrl+C` opens the interactive menu whose option `2. send an event` fires it (`client/Main.java` `registerSignalHandler`). `docs/OnelinerGuide.md` has been updated to state this flow explicitly. Tutorials using `count` (T1 "go deeper", T2) should demonstrate the Ctrl+C → send-event interaction — it's a nice engagement beat (live counter on demand).

### Wave 1 verification note (this session)

While independently verifying T7 against `btrace-mcp-server` source (not just trusting the
delegated-agent's draft), found that `list_probes` only returns probes a client has **detached**
from — `io.btrace.agent.Client.listProbes()` (agent side) filters on `RemoteClient.isDisconnected()`
— not every probe currently streaming to a connected client. That's the opposite of what the
tool's own MCP description, `docs/MCPServer.md`, and `docs/BTraceTutorial.md` Lesson 13 all
claimed ("lists active probes"). Also found the MCP server exposes no `reconnect` tool, so
`detach_probe` is effectively one-way from an AI assistant's perspective: `list_probes` can confirm
a detached probe is still running, but nothing in the seven-tool set can `send_event` or
`exit_probe` it afterward. Corrected all four places (T7, `docs/MCPServer.md`,
`docs/BTraceTutorial.md` Lesson 13's tool table + example conversation, and
`ListProbesHandler`'s tool-schema description) rather than ship a tutorial that contradicted the
code it describes. Recommend carrying this into the docs-gap-analysis defect register and
considering a `reconnect_probe` tool for a future release.
