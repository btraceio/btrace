## 3. Release mechanics (fixed in this branch)

### 3.1 Release script and workflow read a version line that no longer exists — BLOCKER, fixed

`c354f12b` (2026-04-22) moved the version into the root `build.gradle` `allprojects` block and
removed `project.version` from `common.gradle`. `scripts/release.sh` (`:34,253,360,692,705`
before) and three `release.yml` steps (`:769,1036,1082` before) still grepped and sed-ed
`project.version` in `common.gradle`.

Reproduced in this session: `grep "project.version" common.gradle` → exit 1, so
`get_current_version()` aborts with "Cannot find version in common.gradle". The workflow's
dry-run version update and both post-release snapshot bumps would have been silent no-ops followed
by a failing empty commit.

Fix: `e72c5ad5`. Verified: `DRY_RUN=true scripts/release.sh minor HEAD` (with a stub `gh`) prints
`Release Version: v3.0.0`, `Release Branch: release/3.0._`, `Next develop: 3.1.0-SNAPSHOT`; the sed
on a copy of `build.gradle` changes exactly line 12.

**Operator note:** because develop is already `3.0.0-SNAPSHOT`, the release must be triggered with
`./scripts/release.sh minor`; `major` computes `4.0.0` (verified in the same dry run). Documented in
`docs/releasing.md`.

### 3.2 `btrace --version` printed `(dev)` on every build — fixed

Gradle 9 removed `Project.exec`; `getGitCommit()` in `common.gradle` swallowed the resulting
`MissingMethodException` and returned `dev`, so `btrace --version` read `BTrace v.3.0.0-SNAPSHOT (dev)`
and the client manifest carried `Build-Revision: dev`. Reproduced with a scratch build script
(`Could not find method exec() … on root project`). Fix: `providers.exec` (`057528e3`). Verified by
`:btrace-core:processResources --rerun-tasks`: the resource now contains the commit hash.

### 3.3 Release body

`release.yml` used only `generate_release_notes: true` with no `body_path` and no
`.github/release.yml` categories; for 393 commits (v2.2.6, 2024-11-09 → HEAD) the body would be a
flat PR list dominated by Renovate. This branch adds `.github/release-notes/v3.0.0.md` and a
"Resolve curated release notes" step feeding `body_path` (auto-generated notes are appended). YAML
validated with `yaml.safe_load`.

  `continuous.yml:103` / `release.yml:275` use `27.ea.31-open`, `docs/JDKCompatibility.md` listed
  "27 (EA)", and the canonical support sentence said "Java 8–25+".
- Verified in this session on the JDK 27 GA build: warning gate `PASSED (warnings=0)`; full
  integration suite 72/72 non-skipped tests green (§2.1); `ClassFileApiBackend` handles the
  major-71 class files (ASM ceiling is 69, see below).
- Changed in this branch: the support sentence now reads **"BTrace 3.0 runs on Java 8–27+"** in
  `README.md`, `docs/README.md`, `GettingStarted.md`, `FAQ.md`, `Troubleshooting.md`,
  `QuickReference.md`, `Migration-2.x-to-3.0.md`, the release notes, and drafts B1/B10;
  `docs/JDKCompatibility.md` marks 27 as supported and explains the CI lane.
- **Not changed (maintainer decision):** the CI matrix. `scripts/update-jdk-versions.sh:60-83`
  only advances an `N.ea.*-open` lane to the newest EA major (it will move `27.ea` → `28.ea` once
  SDKMAN lists a 28 EA build) and never adds a GA lane for the promoted major, so 27 coverage would
  silently disappear at that point. Add a `27.0.x-tem` (or `27-open`) lane to both workflows once
  SDKMAN publishes one; until then the EA build is the only 27 lane.
- ASM: `settings.gradle:58` pins ASM 9.10.1, whose `Opcodes` define `V26 = 70` and `V27 = 71`
  (checked with `javap -constants` on the cached jar). `AsmInstrumentationBackend.MAX_ASM_MAJOR_VERSION`
  stays at 69, so Java 26/27 class files are routed to the ClassFile API backend on JDK 24+ agents
  even though the bundled ASM could parse them. That is a deliberate routing choice; raising the
  constant would move Java 26/27 targets back onto the ASM backend and is a maintainer decision,
  not a release blocker. Comments and `InstrumentationBackends.md` that claimed "ASM 9.9.x tops out
  at 69" were corrected.
