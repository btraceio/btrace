# BTrace 3.0.0 Prepared-Mode Authentication Design

Date: 2026-07-13

Status: implementation design for
[#874](https://github.com/btraceio/btrace/issues/874)

Policy dependency:
[`3.0.0-prepared-mode-security-policy.md`](3.0.0-prepared-mode-security-policy.md)

## Scope

Authentication protects the startup-loaded (`premain`) command server before existing V1 or V2
protocol negotiation begins. Dynamically attached (`agentmain`) clients retain the existing
protocol handshake for 2.2.x compatibility. Startup-script mode with `noServer=true` creates no
server endpoint or credentials.

Remote command-server operation is deferred. BTrace 3.0.0 accepts only loopback bind addresses;
wildcard and non-loopback addresses fail agent initialization.

## Version-neutral preamble

Every prepared-mode TCP connection starts with this request:

```text
4 bytes  magic: ASCII "BTA1"
4 bytes  unsigned token length encoded as a positive Java int
N bytes  token
```

The token length must be between 1 and 4096 bytes. The server reads the request under the existing
bounded negotiation socket timeout and compares the supplied token with
`MessageDigest.isEqual`.

The server writes exactly one four-byte response:

```text
ASCII "BTAK"  authentication accepted
ASCII "BTAF"  authentication rejected
```

After `BTAK`, the connection proceeds with the unchanged V1 Java-serialization header or V2
`BTR2` negotiation. Missing magic, invalid lengths, truncated tokens, and incorrect tokens receive
`BTAF` when the socket remains writable, then the server closes the connection. No BTrace command
is decoded before `BTAK`.

This preamble deliberately is not a V1 or V2 command: putting authentication inside either command
codec would require decoding an unauthenticated operational stream and would leave the other codec
unprotected.

## Compatibility

- A 3.0 client dynamically attaching a 2.2.x agent sends no authentication preamble.
- A 2.2.x client dynamically attaching a 3.0 agent uses the existing V1-compatible path.
- A 2.2.x client connecting to a 3.0 prepared agent sends V1 or V2 bytes where `BTA1` is required;
  the server rejects and closes it before decoding a command.
- A 3.0 client reads prepared-mode discovery properties through the Attach API, authenticates, and
  then negotiates V1 or V2 normally.

Authentication failure never falls back to an unauthenticated connection. V2-to-V1 protocol
fallback opens a new socket and repeats authentication before starting V1.

## Endpoint and discovery properties

After the socket is bound and credentials are ready, the agent publishes:

| Property | Value |
| --- | --- |
| `btrace.port` | Actual nonzero bound port, including when configured with `port=0` |
| `btrace.address` | Numeric loopback address used by the server |
| `btrace.auth.required` | `true` for prepared mode; `false` for dynamic mode |
| `btrace.auth.tokenFile` | Absolute token-file path for prepared mode only |

The client adopts the discovered address and port for the selected target PID instead of guessing
the IP family or assuming the configured port survived ephemeral binding.

## Token lifecycle

Prepared mode accepts an optional `authTokenFile=<path>` argument. The argument contains a path,
never a token.

- If the path names an existing regular file, the agent requires it to be owned by the target JVM's
  account with owner-only access, then reads one non-empty token of at most 4096 bytes.
- If the path does not exist, or no path is configured, the agent creates a file, writes a
  cryptographically random 256-bit URL-safe token, and restricts access to the owner.
- POSIX files use `rw-------`. ACL-backed files are restricted and verified through Java NIO. If
  owner-only access cannot be established or verified, prepared-mode startup fails.
- Agent-generated files are deleted on initialization failure and orderly shutdown. User-supplied
  existing files remain in place.
- In-memory token copies are cleared when their owner closes or after a connection authenticates.

Token contents are excluded from process arguments, system properties, normal logs, debug logs,
and exceptions. Discovery publishes only the file path.

## Server lifecycle

Socket binding and credential preparation occur synchronously during agent initialization. The
accept thread starts only after the runtime is ready. Any later initialization failure closes the
socket, clears discovery properties, and removes generated credentials.

Each accepted prepared-mode socket authenticates under the bounded negotiation timeout. Failed
connections are closed before the accept loop continues. Shutdown closes the listening socket,
clears the discovery properties, wipes the in-memory token, and removes generated credential
material.
