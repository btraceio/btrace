# Enforced probe budgets — design

Date: 2026-11-14

Status: approved 2026-11-14

Base: `origin/develop` c968df58

## Intent

BTrace's verifier checks what a probe handler may do. It does not check what the probe costs or how
long it stays. Tutorial 12 shows an empty handler on a hot method taking a JVM from about 60M to 7M
calls/s, and a detached probe stays installed until someone removes it. With an AI assistant
deploying probes through the MCP server, "narrow scope, remove it when done" is guidance in skill
text and nothing enforces it.

This change lets the operator of a JVM set limits that the agent enforces by itself: a probe that
runs too hot or too long is switched off, removed, and the deployer is told why. That is the piece
that makes "safe to let an agent touch production" a property of BTrace rather than of the caller.

## Goals

- An operator can set, at JVM launch, a per-probe **time-to-live** and a per-probe **hit-rate
  ceiling**.
- When a probe exceeds either, the agent stops its handlers immediately, removes its
  instrumentation through the normal exit path, and reports the reason.
- With no limit configured, behavior and per-hit cost are unchanged from today.
- Works on every supported JDK tier and with both instrumentation backends, with no change to
  generated bytecode.

## Non-goals (this change)

- CPU-time or latency budgets. Handler timing would miss the call-site dispatch cost that
  dominates in tutorial 12.
- A cap on how many classes or methods a probe may match. That is a deploy-time check and a
  separate change.
- A per-deploy limit requested by the client, and a structured "probe removed" command. Both need
  a wire-protocol field; see Follow-ups.
- Keys in `permissions.properties`. Agent arguments and system properties only.
- Changes to the MCP server in `btraceio/agent-plugins`.

## Anti-goals

- **Silent degradation.** A budget must never thin or drop handler calls quietly. It either lets
  the probe run or removes it and says so.
- **Fail open.** If budget enforcement cannot be set up for a handler, that handler must not run
  uncounted. This mirrors `HandlerRepositoryImpl.applyLevelGuard`, which disables a handler whose
  guard cannot be built.
- **A deployer raising its own limit.** No client-supplied value may loosen what the operator set.
- **Removal work on an application thread.** The hot path only counts. Retransformation and I/O
  happen on an agent thread.

## Constraints

- Main code targets Java 8; no fully qualified type names in source; Spotless / Google Java Format.
- User-visible, cross-process behavior needs end-to-end coverage in `integration-tests` (run with
  `-Pintegration`), and each new test must be seen to fail against code without the feature.
- No wire-protocol or public-API change in this step. New agent options are additive.
- `btrace.jar` is a masked JAR; new classes must land in the right section
  (`docs/architecture/MaskedJarArchitecture.md`).
- The probe exit path is delicate. Read
  `internal/specs/2026-09-27-issue-932-exit-path-wedge-fix-design.md` and
  `RemoteClient.completeTerminalExit` before touching it.

## Approaches considered

**A. Wrap the handler method handle at resolve time — chosen.**
`HandlerRepositoryImpl.resolveHandler` is the single place every handler handle is produced, for
both backends, and the result is cached per handler on the probe. `applyLevelGuard` already
composes handles there. A counting wrapper is one more composition in the same place. No bytecode
change, so the golden instrumentation data and the ClassFile API backend are untouched. Trade-off:
counts are per handler (here: per probe), not per call site, and they count handler executions
after `@Sampled` and `@Level` have had their say, not raw method entries.

**B. Inject a counter in the instrumented bytecode.**
Gives per-site counts and sees every entry. Rejected for now: it must be written twice
(`MethodTrackingContext` for ASM, `ClassFileApiBackend` for JDK 24+), regenerates golden data, and
lands in the least-tested code in the repository. Remains a possible refinement if per-site
attribution is needed.

**C. Force adaptive sampling as the limiter.**
Rejected: the adaptive interval is capped at 1,500 (`MethodTracker`), so it is not a ceiling; it
changes results silently; and it needs B's bytecode path anyway.

Jaroslav picked A on 2026-11-14, and picked "operator owns the limit" over "deployer sets it".

## Design

### Configuration (decided: operator-owned, launch-time)

Two new settings, each available as an agent argument and as a JVM system property:

| Agent argument | System property | Meaning | Default |
| --- | --- | --- | --- |
| `probeTtl=<seconds>` | `io.btrace.probeTtl` | maximum lifetime of a probe, from deploy | unset = no limit |
| `probeMaxRate=<hits/s>` | `io.btrace.probeMaxRate` | maximum executions per second of the handlers one probe attaches to application code (handlers the runtime calls itself, such as timers and events, are not counted) | unset = no limit |

Precedence (amended 2026-11-14 after code review): a system property set on the target JVM is the
operator's ceiling. Agent arguments count only when the agent is loaded at JVM launch (prepared
mode and startup-script mode), where the operator wrote them: there they can tighten the property,
and the effective value is the smaller of the two. Under dynamic attach the attaching client
supplies the agent arguments and is not the operator, so `probeTtl` / `probeMaxRate` arguments are
ignored with one line. Otherwise the first attacher could impose a budget, and with it the refusal
of trusted mode, on every later deploy until the JVM restarts.

Limits are fixed when the agent loads. A later attach to a JVM that already has the agent cannot
change them.

Second agent load (added 2026-11-15 after an independent review): every `premain`/`agentmain`
call gets a fresh agent class loader (`Loader.startAgent`), so an agent loaded a second time is a
separate instance that knows nothing of the first one's limits. A budget set only by launch-time
agent arguments was therefore invisible to it, and an attacher loading the agent directly got an
unbudgeted, trustable agent. The agent loaded at launch now writes its resolved limits (or the
invalid launch argument) to the two system properties, which every instance reads; the later
instance is in attach mode, so it can neither raise nor remove them.

Trusted argument ordering (added 2026-11-15): under dynamic attach with an operator property set,
`trusted=true` is not applied at all while the agent arguments are parsed, instead of being set
and cleared afterwards. Otherwise `btrace.system.appendJar`, which requires trusted mode, was
honoured during parsing. The hints that name the ways to enable trusted mode leave out the
client's `-u` flag when a budget is requested, because it is refused then.

Reconnect (added 2026-11-15): a client cannot reconnect to a detached probe once its budget has
tripped; it gets a refused reconnect instead of a connection that drops when the probe is removed.

Known limit: `SharedSettings.GLOBAL` is shared by all agent instances in a JVM. If the operator
launched with `trusted=true` and a budget, a second agent load by an attacher clears that shared
flag, and later deploys through the first agent are verified. This fails toward less trust.

Protecting the ceiling — *my call*: `Main.parseArgs` turns any `$key=value` agent argument into
`System.setProperty` (`Main.java:1213-1215`), so an attaching client could overwrite the operator's
property. The two `io.btrace.probe*` properties are therefore read once, before agent arguments
are parsed, and a `$io.btrace.probeTtl` / `$io.btrace.probeMaxRate` agent argument is rejected
with a one-line message.

Invalid values (non-numeric, zero, negative) — *my call*, fail closed for whoever the operator is:

- An invalid **system property**, or an invalid agent argument in **premain** mode (prepared or
  startup-script): one line naming the option, and the command server is not started, as for an
  invalid `port=` today (`Main.java:329-336`). An operator who mistyped a limit must not get an
  unlimited agent.
- An invalid agent argument under **dynamic attach**: one line naming the option, the argument is
  ignored, and the system-property ceiling still applies. The agent latches on first load, so
  refusing to start the server here would leave the JVM unreachable until restart because of a
  deployer's typo.

### Trusted mode (decided 2026-11-14, after the whole-change review)

A probe run in trusted mode is not verified and can run arbitrary code, including code that stops
the governor. So when any limit is in effect, trusted mode that does not come from the operator
is not available:

- A client asking for it over the protocol (`btrace -u`) is refused. The deploy fails with one
  line naming the cause; it is never downgraded silently to verified mode.
- `trusted=true` supplied as an agent argument under dynamic attach is ignored, with one line
  logged in the target JVM, and every probe is verified. It is not refused outright because agent
  arguments are fixed on first load: a refusal would block every later verified deploy until the
  JVM restarts. A probe that needs trusted mode then fails verification with the usual error.
  This covers probes loaded from attach-time `script=` / `scriptdir=` as well as clients that
  connect later.

`trusted=true` written by the operator at JVM launch is still honored: that operator has opted
out of the guarantee. With no limit configured, trusted mode is unchanged.

### Counting

- One counter per probe, shared by all of its handlers.
- In `resolveHandler`, when a rate ceiling is in effect, compose the resolved handle with a step
  that increments the probe's counter, then cache the composed handle as today. Compose it
  *inside* the level guard so only handlers that actually run are counted.
- When no rate ceiling is in effect, do not add the step.
- Whether the step is added depends only on whether a rate ceiling is configured, never on the
  kind of client. `resolveHandler` does not need to know who deployed the probe.
- If composing fails, disable the handler and log at error, as the level guard does.
- Counter type — *my call*: `LongAdder`. A plain racy field is cheaper but undercounts under
  contention, which fails toward not tripping. The benchmark below decides whether that default
  holds.

### Enforcement: the governor

- One daemon thread in the agent, started only when at least one limit is configured.
- Ticks once per second. For each live probe it checks:
  - **TTL:** time since deploy against `probeTtl`.
  - **Rate:** counter delta since the previous tick against `probeMaxRate`. One window over the
    ceiling trips the probe.
- On trip, in this order:
  1. Mark the probe as tripped, then call `IndyDispatcher.invalidateProbe`. The mark makes
     `resolveHandler` return a no-op for that probe from then on. Without it, only call sites that
     are already linked stop: the probe stays in `probeMap` until exit, so a site that links later
     would resolve the cached handler and run it.
  2. One message line to the client over the existing message channel, naming the probe, the limit
     and the observed value, for example
     `BTrace: probe OrderTiming removed: 412000 hits/s exceeded probeMaxRate=10000`.
     The same line is logged at WARN in the target JVM, so a detached probe's removal is recorded.
  3. The normal probe exit, with a distinct, documented non-zero exit code, so the CLI and the MCP
     server can tell a budget removal from a clean exit. This must go through the same path a
     probe-initiated exit takes, so the terminal handshake and retransformation behave as they do
     today.
- Detached probes are subject to both limits. This is the case TTL exists for.
- Removing a **detached** probe — *my call, please check*: the normal exit does not work here.
  With no transport attached, `RemoteClient.onCommand` returns early and drops the urgent
  `ExitCommand` (`RemoteClient.java:421-427`), so `completeTerminalExit` and `Client.onExit` never
  run and the instrumentation stays. For a detached probe the governor therefore tears down the
  runtime and then calls `Client.onExit` directly. There is no peer, so there is no handshake to
  complete. The connected-probe path is not changed. Afterwards the probe is gone from `CLIENTS`:
  it no longer appears in the probe list, and a reconnect attempt gets today's "no such probe"
  answer. The WARN line in the target log is the only record of why.
- Startup-script probes (decided 2026-11-14, replacing an earlier blanket exemption): a probe
  loaded from `script=` / `scriptdir=`, or bundled with the agent, is exempt from enforcement only
  when the agent was loaded at JVM launch. Those are operator-reviewed and usually meant to run
  for the life of the JVM. Under dynamic attach the same arguments come from the attacher, who is
  not the operator, so such probes are subject to both limits like any other. Exempt means the
  governor skips them, and their handlers are not counted either. A
  budgeted startup-script probe has no client to tell: its removal is recorded in the target's
  log, as for a detached probe.

### What the user sees

```
$ java -javaagent:btrace.jar=port=0,probeMaxRate=10000,probeTtl=600 HotLoopApp.java
$ btrace <PID> HotPathProbe.java
[probe] attached
BTrace: probe HotPathProbe removed: 7100000 hits/s exceeded probeMaxRate=10000
$ echo $?
<budget exit code>
```

## Verification

- **Unit:** counting wrapper increments once per handler execution and not when the level guard
  rejects; wrapper absent when no ceiling is set; handler disabled when composition fails.
- **Unit:** governor with an injected clock — TTL trip, rate trip, no trip below the ceiling,
  tighten-only precedence, invalid values rejected.
- **Integration (`-Pintegration`):**
  - hot-loop target with `probeMaxRate`: client receives the message and the budget exit code, and
    the probe is gone afterwards;
  - `probeTtl` with a detached probe: it is removed without a client;
  - no limits set: an existing functional test still passes unchanged.
  Each must be shown to fail with enforcement disabled.
  Also: a call site that links after the trip runs no handler; a `$io.btrace.probeMaxRate` attach
  argument cannot raise an operator ceiling; an invalid attach argument leaves the server running
  with the operator ceiling in force.
- **Benchmark (not done):** the per-hit cost of the counter, which decides `LongAdder` versus a
  plain field, is unmeasured. `benchmarks/agent-benchmark` `BTraceBench` deploys with
  `noServer=true,script=…`, the exempt startup-script mode, and an exempt probe is not counted,
  so that benchmark cannot show the cost. Measuring it needs a benchmark that deploys its probe
  through a client.
- **Gates:** `./gradlew build`, `spotlessCheck`, integration matrix on the JDK tiers available
  locally via `TEST_JAVA_HOME`.

  entry for either. Not verified to be a bug.
